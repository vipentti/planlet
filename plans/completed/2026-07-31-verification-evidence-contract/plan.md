# Verification Evidence Contract

## Summary

Make Planlet's verification-evidence lifecycle explicit: `plan.md` owns static verification
strategy, task checkboxes remain the progress gate, and an optional concise
`## Verification Evidence` section in `tasks.md` records material, failed, partial, unavailable,
or externally governed outcomes. CLI behavior is unchanged.

## Scope

- Canonical skills under `skills/` (`planlet-plan`, `planlet-implement`, `planlet-complete`),
  their reference guidance and templates.
- Generated harness copies under `.agents/skills` and `.claude/skills`, regenerated with the
  built project CLI.
- Regression coverage for opaque evidence notes and for the skill contract and scenario suite.
- Durable contract wording in `planlet_design.md`, `README.md`, and `AGENTS.md`.

## Out of Scope

- Any new CLI command, evidence schema, model field, error code, database, or third plan file.
- Changes to the CLI-generated `## Completion` record, which stays lifecycle-only.
- Provider-specific integrations (CI, PR, registry APIs).
- Retroactive rewrites of completed planlets and the one-time `origin/feature/p5` migration,
  which is separate follow-up work.

## Approach

Use the existing allowed surface: `tasks.md` already permits free-form Markdown outside
recognized task lines, and the task parser ignores it. Adopt a convention, not a schema.

Responsibilities stay distinct:

- `planlet-plan` writes strategy only: stable repository command names or check categories,
  expected outcomes, external gates, limitations, and a no-log evidence policy. It never appends
  execution results.
- `planlet-implement` maintains the optional `## Verification Evidence` section in `tasks.md`
  before completion, with short outcome lines, immutable commit SHAs, and stable full URLs when
  material. Task checkboxes remain the authoritative progress gate.
- `planlet-complete` inspects and reports the optional section without parsing its semantics,
  rerunning checks, or creating proof.

Canonical skills are edited first, then harness copies are regenerated with the built CLI.

## Acceptance Criteria

- `planlet-plan` guidance states that `Verification` is strategy, names the no-log and
  stable-anchor policy, and does not direct planners to record run results in `plan.md`.
- `planlet-implement` guidance directs a concise optional `## Verification Evidence` section in
  `tasks.md`, written before completion, preserving existing task lines and IDs, with failed,
  partial, or unavailable checks leaving affected tasks unchecked.
- `planlet-complete` guidance reports the optional section as inspected evidence, distinct from
  the CLI completion audit, and adds no evidence parsing or check reruns.
- `.agents/skills` and `.claude/skills` are byte-identical to canonical sources, with manifests
  regenerated by the built CLI.
- A planlet whose `tasks.md` contains a free-form `## Verification Evidence` section parses with
  unchanged task IDs, counts, and status, and the section survives both normal and incomplete
  completion into the archive.
- Skill contract and scenario coverage asserts strategy-only plan wording, concise evidence
  guidance, no-log and stable-link wording, and failed verification leaving tasks unchecked.
- `planlet_design.md`, `README.md`, and `AGENTS.md` state the contract without describing a CLI
  feature that does not exist.

## Verification

- Local: repository commands `npm run format:check`, `npm run lint`, `npm run type-check`,
  `npm run build`, and `npm test`, plus `git diff --check` and `git status --porcelain`.
- Generated-skill parity: `node dist/planlet.mjs update --tools all` followed by
  `git diff --exit-code -- .agents .claude`; existing byte-identity tests must pass.
- Planlet self-check: `node dist/planlet.mjs validate verification-evidence-contract`.
- No external CI, registry, or release evidence is in scope for this change.
- Record material results in `tasks.md` as concise outcome lines; never paste logs.

## Risks and Considerations

- Agent-maintained prose can go stale; the CLI cannot validate its accuracy. Accepted, because
  skills own judgment and Git preserves note history.
- Skill text is asserted by contract tests, so wording changes must stay consistent with the
  assertions added here.
